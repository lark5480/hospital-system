# 多 Agent 团队协作代码审查系统（SOP）

> 用途：对任意一次变更（PR / 迭代 / 全量体检）执行「安全 · 性能 · 测试」三维度并行审查 + 交叉质询 + 主席收敛，产出统一的、可追溯的问题清单。
> 本次执行记录：见 [`2026-09-08-code-review-report.md`](./2026-09-08-code-review-report.md)。

---

## 一、团队构成

| Agent | 代号 | 唯一职责 | 明令禁止 |
|---|---|---|---|
| 安全审计 | SECURITY | 漏洞、注入、越权、敏感数据泄露、认证/会话、配置与依赖 | 不得输出性能调优或覆盖率建议（可指出安全含义，但要标注"建议 PERF/TEST 立项"） |
| 性能分析 | PERFORMANCE | 算法复杂度、N+1、索引与执行计划、锁与事务、资源泄漏、启动开销 | 不得把越权/泄露当主结论 |
| 测试质量 | TESTING | 覆盖率缺口、边界条件、可测试性、测试分层、CI 工程化 | 不得重复出条安全/性能项 |

**为什么必须禁止越界**：首轮实测中，三个 Agent 的清单天然会在同一处代码聚集（如 `PatientController.list()` 既是越权出口又是全表扫描源，还缺契约测试）。若允许越界，同一问题会被三个 Agent 以不同编号各写一遍，收敛时无法判断是"三个问题"还是"一个问题的三个面"。禁止越界 + 交叉质询时的"迁移"机制，是让重叠可控的关键。

## 二、流程（三轮）

```
R1 独立审查 ──▶ R2 交叉质询 ──▶ R3 主席收敛
   3 个 Agent        3 个 Agent        人工/主席
   各自 15 条        反驳+升级+补充     裁决分歧、合并同源、定稿
```

### R1 · 独立审查（并行）
三个 Agent 同时开工，互不知情。每个 Agent 输出：
1. 最多 15 条发现，严格按格式（见第三节）
2. `## 待人工复核`：代码无法判定、需要实测/运维确认的点（3-5 条）
3. `## 我主动排除的疑点`：**看起来可疑但实际没问题的点 + 排除理由**（2-3 条）

第 3 项是整套机制的**反幻觉核心**。它强制 Agent 把"我查过但否掉了"的结论显式化，收敛时能区分"没发现"和"发现了但判定无风险"，也避免下一轮有人把已排除项当新发现重复提出。

### R2 · 交叉质询（并行）
每个 Agent 收到**另外两个 Agent 的完整清单**，输出五段：
- **A 反驳与降级**（≥3 条）：挑出他人夸大/误判的项，给证据 + 建议定级
- **B 升级与迁移**（≥2 条）：挑出他人清单中属于自己维度的问题，迁移立项
- **C 新发现**（≥3 条）：受他人视角启发、自己第一轮遗漏的问题
- **D 自我修正**（≥3 条）：自己的哪些条要降级/升级/撤回，为什么
- **E 预判辩护**：预设他人会质疑自己的哪些条，逐条回应

**关键约束**：凡要反驳他人结论，**必须先用工具打开源码核实**并引用 `文件:行`。禁止凭印象否定他人。实测中这条约束直接纠正了两处事实错误（"零索引"实为 27 张表 2 张有索引；"MyBatis SQL 打印"实为从未开启）。

### R3 · 主席收敛（串行，人工或主席 Agent）
1. **合并同源**：不同 Agent 命中同一处代码的，合并成一条并交叉引用（如 SSE 问题 = SEC-16 + PERF-10）
2. **裁决分歧**：三方各执一词时按第四节规则裁决，并把**裁决理由**写进报告
3. **复核关键事实**：主席对争议最大、级别最高的几条亲自读源码验证
4. **定稿**：统一编号、按严重度排序、生成路线图与前置依赖

## 三、输出规范

### 单条发现的必备字段
```
### [维度前缀-序号] 一句话标题
- **位置**：`相对路径:行号`
- **类别**：该维度的子分类
- **严重度**：Critical | High | Medium | Low
- **置信度**：高 | 中 | 低
- **证据**：3-8 行关键代码片段
- **影响/攻击场景/量化影响**：按维度选一
- **建议**：可落地的代码级方案
```

### 定级标准（按维度微调，但严重度口径统一）
- **Critical**：可直接导致批量敏感数据泄露 / 权限完全失守，或线上必然不可用
- **High**：需低门槛前置条件即可造成实质损害，或数据量到 10 万级必然劣化
- **Medium**：特定条件叠加才触发，或属可被利用的放大器 / 工程化缺失
- **Low**：最佳实践偏离、后门代码路径、局部体验问题

各维度的补充判据：
- 安全：按「获取前置条件的成本 × 影响面」定级。弱口令 + 零归属校验 = 高，因为门槛极低
- 性能：按「数据量增长到 10 万级时的实际影响」定级，必须给放大倍数或复杂度
- 测试：按「出 bug 后能否被现有测试拦住」定级。**静默性**（违反契约但不报错）是立项的必要条件——必然抛异常的问题不需要测试也能暴露

## 四、分歧裁决规则（R3 适用）

| 情形 | 裁决原则 |
|---|---|
| 一方给机理、另一方给现象 | **采纳机理方**。例：审计丢失，SEC 说"事务回滚抹掉"、TEST 说"异常短路"——复核代码后按 TEST 修（改 `try/finally` 而非加 `REQUIRES_NEW`），因为修法由机理决定 |
| 一方要求降级、另一方沉默 | **降级**。沉默视为无异议 |
| 两方都认为对方措辞夸大 | **保留结论、修正措辞**。例："全部表零索引" → "27 张表仅 2 张有二级索引" |
| 一方要求迁出、另一方要求保留 | **拆分**。降级的那部分迁出，剩余部分另立新条（例：TEST-10 → Low 迁安全 + 新立 TEST-10b Medium） |
| 一处代码两个维度都有理 | **合并计数、交叉引用**，明确"一次修复关闭两条"，避免重复派工 |
| Agent 之间事实冲突 | **主席亲自读源码**。不得靠投票决定 |

## 五、复用：如何对新的 PR / 模块重跑

1. **确定范围**：本次是全量体检；日常可只对 diff 涉及的文件跑（把"必读范围"换成 PR 的变更文件清单）
2. **并行启动 3 个 Agent**：使用本仓库的 `code-explorer` 子代理（自带 lsp / search / read），为每个 Agent 套用下面的角色提示词骨架
3. **收集 R1 输出 → 组装 R2 提示词**：把另两方的清单**压缩成"编号 + 标题 + 严重度 + 一句话核心论点"**后塞给质询方（实测：全量粘贴会稀释注意力，压缩后质询质量更高）
4. **主席收敛**：按第四节裁决，产出报告

### 角色提示词骨架（复用时替换 `{}` 内容）
```
你是多 Agent 代码审查团队中的{维度} Agent（代号 {CODE}）。
这是第 {1|2} 轮{独立审查|交叉质询}。其他 Agent 负责{另两个维度}，请勿越界。

## 审查对象
仓库：{repo_path}
技术栈与架构摘要：{...}

## 必读范围（必须用工具真实打开源码，禁止臆测）
{文件/目录清单}

## 审查清单
{该维度的 6-8 个检查方向}

## 输出格式
{见本文件第三节}
{第 2 轮时追加 A/B/C/D/E 五段要求}
```

### 已知坑位（本次实测总结）
- **并行调用会触发限流**：同一批并行启动 3 个子代理可能返回 429，需改为串行逐个启动
- **子代理记忆不跨轮次**：R2 的 Agent 不记得自己 R1 说了什么，必须在提示词里附上它自己的编号清单才能做"自我修正"
- **数字类结论要交叉验证**：本次"测试类数量""索引数量"两个事实都在质询中被相互纠正，涉及统计的结论至少让第二个 Agent 复核
- **质询方容易只反驳不补充**：必须在提示词里硬性要求"新发现 ≥3 条"，否则 Agent 会退化成纯挑刺
